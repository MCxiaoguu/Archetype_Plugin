# oauth

## summary
Device-flow OAuth subsystem for the Archetype backend (Flask). Blueprint `oauth_bp` defined in /Users/hanyanggu/Personal_Files/Coding/Archetype_all/Archetype_Core/Archetype_Backend/api/routes_oauth.py, mounted at prefix `/api/oauth` in app.py:52. The backend is a THIN PROXY to Auth0: /device/code POSTs form data to `https://{AUTH0_DOMAIN}/oauth/device/code` (routes_oauth.py:96-102) and /device/token POSTs `grant_type=urn:ietf:params:oauth:grant-type:device_code` to `https://{AUTH0_DOMAIN}/oauth/token` (routes_oauth.py:165-177), returning Auth0's JSON body and status code verbatim (routes_oauth.py:122, 186). SERVER-SIDE TOKEN STORAGE: NONE. Tokens are never persisted server-side (no Mongo writes anywhere in routes_oauth.py) — the client (plugin) is instructed to persist access_token/refresh_token in the OS keychain (docs/DEVICE_AUTH_PLUGIN_INTEGRATION.md:288-291, 312-314). Auth0 is the sole source of truth; validation is stateless JWT verification. VALIDATION ON PROTECTED ROUTES: `require_auth` decorator in /Users/hanyanggu/Personal_Files/Coding/Archetype_all/Archetype_Core/Archetype_Backend/infrastructure/auth/jwt_validator.py:103-163 — extracts `Authorization: Bearer <t>` (get_token_from_header, jwt_validator.py:46-56), then decode_token (jwt_validator.py:59-100): PyJWKClient against `https://{AUTH0_DOMAIN}/.well-known/jwks.json`, RS256 only (ALGORITHMS, line 22), audience=AUTH0_AUDIENCE, issuer=`https://{AUTH0_DOMAIN}/`, leeway=120s. On success sets `request.user_id = payload['sub']` (jwt_validator.py:160), which all data-scoped queries use. Failure reason recorded on `request._auth_error` (jwt_validator.py:69-74) and surfaced by /validate-token as `reason`. DEV SHORTCUT: per-request dev bypass `_is_dev_bypass_allowed()` (jwt_validator.py:25-43): active when (DEV_MODE in {1,true,yes} AND FLASK_ENV != "production") OR when AUTH0_DOMAIN is unset/placeholder "your-domain.auth0.com" (and FLASK_ENV != production). When active, require_auth skips JWT entirely; user_id resolution order (jwt_validator.py:129-142): 1) `X-User-Id` header (impersonate anyone), 2) Bearer token sub if a real token is sent, 3) JSON body `auth0Id`/`userId`, 4) fallback literal `dev-user-123`. There is NO auto-approve of the Auth0 consent step itself — a human must open verification_uri_complete in a browser even in dev (the E2E test at _tests/test_device_oauth_flow.py:104 requires manual approval). ENV VARS: AUTH0_DEVICE_AUTH_DOMAIN (falls back to AUTH0_DOMAIN), AUTH0_DEVICE_AUTH_CLIENTID / AUTH0_DEVICE_AUTH_CLIENT_ID (falls back to AUTH0_CLIENTID / AUTH0_CLIENT_ID), AUTH0_AUDIENCE (routes_oauth.py:40-63); DEVICE_AUTH_PUBLIC_BASE + DEVICE_AUTH_PUBLIC_PATH (default "/device-auth") rewrite verification_uri{,_complete} to a branded URL (routes_oauth.py:111-120); DEV_MODE, FLASK_ENV, PORT, HOST, BACKEND_PORT/BACKEND_URL/EXTERNAL_BACKEND (test only). ## endpoints
- POST (also GET) /api/oauth/device/code | auth: none | req: Optional JSON body or query params: {scope?: string (default "openid profile email offline_access"), audience?: string (default env AUTH0_AUDIENCE = archetype-backend-api)}. Empty body {} is fine. routes_oauth.py:66-122 | resp: Auth0 device-code response verbatim, status passed through (200 on success): {device_code, user_code, verification_uri, verification_uri_complete, expires_in (900), interval (5)}. verification_uri{,_complete} rewritten to DEVICE_AUTH_PUBLIC_BASE + DEVICE_AUTH_PUBLIC_PATH when DEVICE_AUTH_PUBLIC_BASE set (routes_oauth.py:111-120). Errors: 500 {error:"auth0_not_configured", message}; 502 {error:"auth0_unreachable", message}; 502 {error:"auth0_bad_response", message}; Auth0-side errors (e.g. unauthorized_client) proxied with Auth0's status code.
- POST /api/oauth/device/token | auth: none | req: JSON body {device_code: string} (also accepted as form field device_code). routes_oauth.py:141-186 | resp: Auth0 token response verbatim, status passed through. Pending: 403 {error:"authorization_pending"|"slow_down", error_description}. Success: 200 {access_token (RS256 JWT), id_token, refresh_token? (only with offline_access scope), token_type:"Bearer", expires_in: 86400, scope}. Terminal (restart flow): 403 {error:"expired_token"} (user too slow), 403 {error:"access_denied"} (user denied), 400 {error:"invalid_grant"} (bogus/already-redeemed device_code). Local errors: 400 {error:"missing_device_code", message}; 500 {error:"auth0_not_configured"}; 502 {error:"auth0_unreachable"|"auth0_bad_response"}.
- POST (also GET) /api/oauth/validate-token | auth: token supplied via Authorization: Bearer header, OR JSON body {token}, OR ?token= query param | req: No body needed if Authorization header present. routes_oauth.py:189-221 | resp: 200 {valid:true, user_id (sub), audience, issuer, expires_at (exp), issued_at (iat), scope, payload (full decoded JWT)}. 400 {valid:false, error:"missing_token"} if no token anywhere. 401 {valid:false, error:"invalid_token", reason: string from request._auth_error e.g. "InvalidTokenError: ExpiredSignatureError: Signature has expired"}. Uses same decode_token/JWKS path as require_auth, so 200 here guarantees protected routes accept the token.
- GET /api/oauth/device-auth | auth: none (user's browser, not the plugin) | req: Query param user_code=XYZ. routes_oauth.py:125-138 | resp: 302 redirect to https://{AUTH0_DOMAIN}/activate?user_code=XYZ (or /activate without param). Branded redirector so verification URL lives on the Archetype domain.
- GET /api/oauth/me | auth: @require_auth (Bearer JWT; dev bypass applies) | req: No params. routes_oauth.py:224-231 | resp: 200 {user_id: request.user_id, message}. 401 {error:"Authorization header missing", message:"No token provided"} or 401 {error:"Invalid token", message:"Token validation failed"} from require_auth (jwt_validator.py:150,154).

## dataModels
- NONE in this subsystem — no Mongo collections touched. Tokens are NOT stored server-side; /device/token proxies Auth0 and returns the token to the caller, which persists it client-side (docs recommend OS keychain: keytar/keyring, DEVICE_AUTH_PLUGIN_INTEGRATION.md:288-291,312-314).
- Implicit auth contract object attached per-request by require_auth: request.user_id = JWT `sub` claim (e.g. "auth0|690fba08a182d00e0c60fd31") — jwt_validator.py:160 (prod) / :142 (dev bypass, may be X-User-Id header value, body auth0Id/userId, or "dev-user-123"). request._auth_error = string failure reason (jwt_validator.py:69-74).
- JWT payload shape returned by /validate-token: {sub, aud (may be array, e.g. ["archetype-backend-api", "https://dev-wddzbb8plcpl8gyj.us.auth0.com/userinfo"]), iss ("https://dev-wddzbb8plcpl8gyj.us.auth0.com/"), exp, iat, scope}

## gaps
- No server-side token/session persistence: issued device-flow tokens are not recorded in Mongo, so there is no server-side registry of authenticated plugin installs/devices. If result-ingestion needs per-device attribution beyond the JWT sub, that must be built.
- No backend refresh endpoint: refresh_token exchange requires the plugin to call Auth0 directly with a hard-coded client_id (docs:316-322). A backend /api/oauth/refresh proxy does not exist.
- No revocation/logout endpoint: nothing to invalidate a stored token server-side; validate-token only checks signature/expiry/audience.
- Nothing here handles session-replay ingestion, persona generation, or plugin test-run instruction serving — this subsystem is purely the auth transport. It does, however, already give the plugin the exact identity primitive needed: any new ingestion route decorated @require_auth gets request.user_id (Auth0 sub) for free, and the docs (DEVICE_AUTH_PLUGIN_INTEGRATION.md:229-236) reference existing protected route families the plugin is expected to call: GET/POST /api/features, /api/persona/*, /api/session/*, /api/uat/* — these are the likely mount points/patterns for persona-enriched instruction serving and result ingestion, but were not read in this pass.
- Dev bypass quirk: if AUTH0_DOMAIN is unset/placeholder and FLASK_ENV != production, auth is silently bypassed regardless of DEV_MODE (jwt_validator.py:39-42) — new plugin-facing routes inherit this.
- validate-token accepts token via query param (?token=) — tokens can leak into access logs; avoid that path in the plugin.
- No rate limiting or interval enforcement on /device/token polling server-side; the backend proxies every poll to Auth0 (Auth0's slow_down is the only throttle).
- POST-only semantics not enforced: /device/code and /validate-token also accept GET (routes_oauth.py:66,189), diverging from the docs which show POST only.
