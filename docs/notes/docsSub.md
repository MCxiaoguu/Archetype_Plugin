## gaps
- Session-replay INGESTION: nothing exists. Frontend PostHog (main.tsx:10-18) records Archetype's own users (consent-gated, CookieBanner.tsx) — it does not ingest customer/product session replays. Backend infrastructure/MCP/posthog_mcp.py is marked 'Status: PLANNING ONLY' (line 7) and is egress-only (capture_event/insight/cohort stubs); no API to pull PostHog recordings. No upload endpoint, no replay storage collection.
- Persona-from-replay: no code path. Persona generation is distribution-sampling + LLM few-shot from segment stats (persona/persona.py, Workflow.md:35-73). The 'Existing Users / With Priori' branch of the persona workflow is 'TBD' (Workflow.md:74-75) — this is exactly the slot for replay-derived personas.
- Onboarding wizard for replay connection: none. OnboardingTour.tsx is a tooltip UI tour only (localStorage 'onboarding-complete', PostHog flag 'onboarding-tour-enabled', state in WorkspaceShell.tsx:42-116). Closest scaffolding to reuse: QuickStartView.tsx full-page wizard pattern as a /workspace child route (App.tsx:78-86) + wizard-step persistence via POST/GET /api/progress (api/progress.ts, api/routes_progress.py).
- Plugin-driven test runs: POST /api/feature-validation/runs and GET /api/feature-validation/runs/{run_id} are referenced by plugin skills/agent (validate-feature/SKILL.md:19, feature-validator.md:18-20, check-run-status/SKILL.md:13) but DO NOT EXIST in Archetype_Backend — must be built, including the run payload (persona + test goal + feature per Archetype_Plugins/CLAUDE.md intent) and run-status/results schema.
- Plugin results ingestion back into MongoDB: no endpoint, no collection, no schema. Archetype_Plugins/CLAUDE.md states results should be 'sent back to the archetype backend for persistency' but nothing implements it. Existing session_log/steps schema (log_result.py) and the frozen FleetEvent contract (replay spec 2026-04-21:61-98) are the natural shapes to reuse for plugin-run step logs.
- Persona-enriched instruction sets served externally: personas are consumed only internally (services.persona_service -> Celery Notte runner). No endpoint returns a persona+goal instruction bundle to an external actor/plugin.
- Auth mechanism mismatch in plugin docs: skills reference ARCHETYPE_API_KEY (validate-feature/SKILL.md:16, feature-validator.md:17) but the implemented backend auth is Auth0 Bearer tokens obtained via the device flow (routes_oauth.py) and stored in auth.json — the run endpoints need to define which is used.
- Validation-monitor replay endpoint GET /validation-tests/<id>/events (NDJSON) is fully specced (docs/superpowers/specs/2026-04-21-validation-monitor-replay-persistence-design.md) but unimplemented on both sides: backend routes_validation_monitor.py has only monitor-snapshot (line 18) + BTW ask (line 33); frontend useValidationMonitor.ts:301-416 does snapshot->wait-status only, progress hardcoded null (line 414), localStorage vm:cursor not implemented, fixed 500ms retry (line 383/389) instead of specced backoff. Note: this 'replay' = fleet-event timeline reconstruction, distinct from user-session-replay ingestion, but its NDJSON/cursor machinery is directly reusable for streaming instruction sets or run events to the plugin.
- BRAINSTORM/ is empty of substance (two one-line stub files) — no additional design detail there.
