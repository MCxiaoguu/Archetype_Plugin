# personaSub

## summary
Persona subsystem of Archetype_Backend (Flask, blueprint 'persona' mounted at /api/persona per app.py:38-40). TWO generation pipelines coexist. (1) LEGACY (persona/persona.py, serves all HTTP routes via services/persona_service.py): numpy-samples 'meta' personas from Gaussian/categorical segment distributions stored in Mongo Persona.preset (parse_distribution_mongo persona.py:28-110, get_segment_by_name retrieval.py:21-25), then 3 batched LLM stages (objective -> subjective -> descriptive, batch_size 10, temperatures 0.35/0.25/0.6) plus need-generation (gen_persona_need / gen_personas_needs_batch) via LLMClient default provider 'openrouter' model 'openai/gpt-4o-mini'; also one-shot vibe personas (generate_vibe_persona_descriptive) and manual radar-config personas. (2) MVP LLM generator (persona/generator.py generate_persona): 4 stateless Gemini calls (provider 'google', model gemini-2.5-flash, temps 0.6/0.7/0.8/0.7, enable_history=False) producing profile + 10 task episodes + 30 life episodes + 15 knowledge chunks, with rule-based validation/clamping and coherence checks; NOT deterministic (no seed, uuid4 ids) and NOT reachable via any HTTP route — used only by tests and persona/population/generator.py (Sobol-sampled trait-anchored population generation, seed=42 default, anchored profiles + causal episodes). Persona persistence: Mongo DB 'Persona', collections user_personas (docs keyed user_persona_id), user_persona_pools, customized_personas (archetype presets), preset (segment distributions); assignment to tests via Archetype_Test.test.test_meta.persona_pool. Persona -> agent runtime path: contract_from_persona (registry.py) -> PersonaSemanticContract (schemas.py) -> render_seed_card (seed.py, first-person instruction text) + PersonaBootstrapper (bootstrapper.py) which embeds up-to-7 foundation chunks + generated episodes/chunks into Mongo DB 'Memory' collections 'episodes'/'chunks' with ACT-R fields. persona_lookup.py provides lru-cached fetch from Persona.user_personas. NO code consumes session-replay or real behavioral data to build personas (validation_monitor_replay.py is simulation-event replay, unrelated); no plugin instruction-set or plugin-result-ingestion endpoints exist.

## gaps
- NO session-replay ingestion exists anywhere in the persona subsystem. Persona generation inputs are only: (a) segment distribution presets in Mongo Persona.preset, (b) free-text vibe prompts, (c) manual radar slider configs, (d) task need + start_url strings. No code path consumes real user behavioral/replay data. infrastructure/MCP/posthog_mcp.py:112 has only an unchecked TODO '[ ] Support session recording integration'.
- services/validation_monitor_replay.py is NOT user session replay — it replays simulated agent fleet events from Archetype_Test.session_log/btw_log for the validation monitor UI. Do not confuse with the planned session-replay ingestion feature.
- The modern MVP LLM persona generator (persona/generator.py generate_persona, 4 Gemini calls) has NO HTTP endpoint. Only callers: _tests/test_persona_generator.py and persona/population/generator.py:27. All /api/persona routes use the legacy persona/persona.py pipeline (openrouter, gpt-4o-mini default). A persona-from-replay feature would likely want to wire generator.py (its user_description/segment_hint params are natural injection points for replay-derived summaries) into a new route.
- _persist_persona_doc (persona_service.py:143-214) drops MVP-generator-specific fields: generated_episodes, generated_chunks, self_description, browsing_habits, starting_mood, start_url are never persisted to Persona.user_personas by service paths. PersonaBootstrapper (bootstrapper.py:107-124) reads persona.get('generated_episodes')/persona.get('generated_chunks') from the raw payload — so persisting full MVP personas is a prerequisite for bootstrap-from-DB.
- No plugin-facing 'instruction set' endpoint exists. Closest building blocks: render_seed_card(contract) (persona/seed.py:121-191) produces a first-person persona instruction string, and contract_from_persona (registry.py:17) normalizes any stored persona doc — both are pure functions ready to back a GET endpoint serving persona-enriched instructions to a Claude Code plugin.
- No plugin-result ingestion endpoint. Existing result writes are simulation-oriented: simulation_core.log_result (init in app.py:57), Archetype_Test.session_log/btw_log, test docs with test_meta.persona_pool. A new collection + POST route would be needed for plugin run results.
- Bug: create_manual_persona (persona_service.py:624-629) references undefined name `parsed_segment` (only defined inside _generate_manual_persona_payloads at line 780) — NameError at runtime for the non-preview manual persona path.
- Bug/mismatch: POST /api/persona/generate (routes_persona.py:239-243) calls generate_new_persona(demographic_input, segment, ...) but the service signature is (persona_json, persona_type, num_personas, ...) (persona_service.py:70) — segment lands in persona_type and demographic_input must be a parsed {segment:{distributions}} dict.
- Determinism: none in MVP generator (uuid4 ids, LLM temps 0.6-0.8, no seed param). Legacy draw_persona_meta uses unseeded np.random (persona/persona.py:210-226). Only persona/population/generator.py generate_population accepts seed (default 42) for Sobol trait sampling; the LLM calls remain non-deterministic.
- list_personas total_count is len(page) not a real count (persona_service.py:906); persona_lookup caches user_personas docs in an lru_cache(512) with no invalidation (services/persona_lookup.py:23-28) — stale reads possible after persona updates.
- Persona memory preview endpoints were removed: routes_persona.py:871-874 and persona_service.py:13-16 TODOs note services/persona_memory_service.py does not exist; GET /persona/<id>/memories and GET /persona/memories are gone.
