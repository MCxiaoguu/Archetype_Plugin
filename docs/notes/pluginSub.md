# pluginSub

## summary
Archetype_Plugins is a Claude Code plugin (manifest /Users/hanyanggu/Personal_Files/Coding/Archetype_all/Archetype_Plugins/.claude-plugin/plugin.json: name "archetype", version 0.0.1) with 4 skills, 1 agent, 1 hook, and 1 stdio MCP server. It is the "actor" half of the pipeline per CLAUDE.md:9 — intended to receive persona/test-goal/feature from the backend, drive Chrome to test the user's product, and post results back — but ONLY the auth login flow is actually implemented in code; everything else is prose instructions to Claude.

COMPONENTS (all paths absolute under /Users/hanyanggu/Personal_Files/Coding/Archetype_all/Archetype_Plugins/):

1. skills/validation/SKILL.md — handles `/archetype:validation`. Branches on $ARGUMENTS (lines 7-10): empty → call the `archetype-setup__login` MCP tool with empty args object (lines 25-32); non-empty → hand off to validate-feature skill passing $ARGUMENTS as feature identifier. Documents the login flow: token cached at ${CLAUDE_PLUGIN_DATA}/auth.json, validated via POST /api/oauth/validate-token; device flow via POST /api/oauth/device/code then elicitation modal then poll POST /api/oauth/device/token (lines 16-23). Explicitly forbids Claude from simulating the device flow (line 32).

2. skills/validate-feature/SKILL.md — instructs Claude to: read the plugin's `.mcp.json` and env vars ARCHETYPE_PORTAL_URL / ARCHETYPE_API_KEY (lines 15-17) [NOTE: no .mcp.json file exists in the repo]; POST {ARCHETYPE_PORTAL_URL}/api/feature-validation/runs with the feature identifier, capture run id (lines 18-20); poll GET .../runs/{run_id} until terminal state passed|failed|error (lines 21-23); summarize pass/fail, scenario counts, portal link, failing scenarios with assertion messages (lines 24-26). 3. skills/list-features/SKILL.md — resolve portal URL + API key from `.mcp.json`/environment (line 12); GET {ARCHETYPE_PORTAL_URL}/api/features, optional $ARGUMENTS as search query (lines 13-14); render table of id, name, owner, last validation status, last run timestamp (lines 15-16); suggest validate-feature next (line 17).

4. skills/check-run-status/SKILL.md — $ARGUMENTS = run id, fallback to most recent run id seen in session (lines 10-11); GET {ARCHETYPE_PORTAL_URL}/api/feature-validation/runs/{run_id} (line 13); report status (queued|running|passed|failed|error), started/finished timestamps, scenario pass/fail counts, portal UI link (lines 14-18); on failure surface first failing scenario's assertion details (lines 19-20).

Procedure: resolve feature id (line 13-15); verify ARCHETYPE_PORTAL_URL and ARCHETYPE_API_KEY env vars set, fail fast (lines 16-17); POST /api/feature-validation/runs with feature id, capture run id + UI link (lines 18-19); poll /api/feature-validation/runs/{run_id} starting 5s backing off to 30s (lines 20-22); report one-line PASS/FAIL/ERROR verdict, scenario counts, top-3 failing scenarios with assertion messages and file/line if portal returns source locations, portal link (lines 23-28); on failure cross-reference failing scenarios against local repo via Grep/Read and hypothesize regression, no fixes unless asked (lines 29-31). Boundaries: never fabricate ids/results; never write to portal beyond starting runs (lines 34-38).

## howToRun
Prereqs: macOS/Linux, Python 3.10+ (stdlib only), Claude Code CLI. Launch from a directory OUTSIDE the plugin folder (else ${CLAUDE_PLUGIN_ROOT}/${CLAUDE_PLUGIN_DATA} do not resolve): `cd ~ && claude --plugin-dir /Users/hanyanggu/Personal_Files/Coding/Archetype_all/Archetype_Plugins --debug`. Verify with /plugin (archetype enabled), /mcp (archetype-setup running), /help (archetype: namespace). Run wizard: `/archetype:validation` (no args). Point at local backend: `export ARCHETYPE_BACKEND_URL=http://localhost:5001` before launching (README.md:103). Override UA: `export ARCHETYPE_PLUGIN_USER_AGENT="custom/1.0"`. Reset auth: `rm ~/.claude/plugins/data/archetype-*/auth.json`. Hot reload: `/reload-plugins`. MCP server logs go to stderr prefixed `[archetype-setup]` under --debug. Portal skills additionally expect ARCHETYPE_PORTAL_URL and ARCHETYPE_API_KEY env vars to be exported (no code sets or documents defaults for them).

## gaps
- Fetching a persona-enriched instruction set: NOT IMPLEMENTED. CLAUDE.md:9 states the backend should send 'desired persona, test goal, feature etc. setup' to this actor, but no skill, agent, endpoint, or code fetches personas or instruction sets. No GET /api/personas or GET /api/instructions equivalent is referenced anywhere in the repo.
- Driving Claude-in-Chrome browser tools: NOT IMPLEMENTED. No skill or agent mentions any browser/Chrome MCP tool. agents/feature-validator.md:4 tool list is exactly `Bash, Read, Grep, Glob, WebFetch`. The current design delegates all test execution to the remote portal (POST /api/feature-validation/runs); nothing runs tests locally in Chrome despite CLAUDE.md:9 saying the plugin should use 'claude code's inherent ability of using chrome'.
- Posting results back to MongoDB/backend: NOT IMPLEMENTED. No POST of locally produced test results exists. The only backend writes are the three /api/oauth/* calls and the run-start POST (which triggers a server-side run, it does not ingest actor results). agents/feature-validator.md:36-37 explicitly forbids writing to the portal beyond starting runs. CLAUDE.md:9's 'send back to the archetype backend with the results for persistency' has no corresponding endpoint, payload schema, or skill.
- Session-replay ingestion: zero references anywhere in this repo (no replay, rrweb, session, or ingestion code). Entirely greenfield on this side; presumably backend-side in ../Archetype_Core.
- Auth/config split: the three portal skills + agent use ARCHETYPE_PORTAL_URL + ARCHETYPE_API_KEY and instruct Claude to read a plugin `.mcp.json` (skills/validate-feature/SKILL.md:15) that DOES NOT EXIST in the repo (only .claude-plugin/plugin.json exists). Meanwhile setup-server.py uses ARCHETYPE_BACKEND_URL + Bearer token in auth.json. Skills never read auth.json, so the device-flow token is never used for feature/run API calls. A results-ingestion or instruction-fetch skill must pick one scheme (likely Bearer from auth.json) and unify.
- API-key transport unspecified: no file states which header (X-API-Key vs Authorization) carries ARCHETYPE_API_KEY.
- No request/response JSON schemas for /api/feature-validation/runs (start payload shape, run object shape) — skills describe fields in prose only; contract must come from Archetype_Core.
- No token refresh: refresh_token is persisted (setup-server.py:299) but never used; expired tokens force a full re-login via device flow.
- SessionStart hook (hooks/hooks.json:9) only tests auth.json existence — it does not validate the token, does not fetch instructions, and does not trigger login automatically.
- Local result presentation ('handled by the plugin' per CLAUDE.md:9) has no implementation beyond prose report formats in the skills/agent.
- Version drift: plugin.json version 0.0.1 vs setup-server.py SERVER_VERSION 0.2.0 (affects default User-Agent string archetype-claude-plugin/0.2.0).
- /api/uat/... endpoint family named in README.md:131 as protected but never called by any skill — possible intended surface for test-run/results APIs.
